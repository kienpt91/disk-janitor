# Security

## Reporting a vulnerability

Please use GitHub private vulnerability reporting on the repository, or email kienphan.dev@gmail.com. Do not file public issues for vulnerabilities. A report that shows a path escape, a way to delete or move something outside a configured root, a way to obtain an approval without going through the approval step (other than the same-user limits documented below), or a way to inject text into terminal or MCP output is in scope and treated as high priority.

## What this tool protects against

`disk-janitor` exists so that a coding agent can help reclaim disk space without being able to run an arbitrary delete. The design goals, each covered by tests:

- **No default scope.** There are no default roots. Scanning needs at least one explicit `--root`. Roots that are `/`, the home directory itself, a parent of the home directory, a system directory or a protected location are refused.
- **Read-only first.** `scan` and `plan` never modify anything (a plan is a JSON file in the state directory). `apply` needs a plan, and a plan needs an approval bound to its SHA-256 digest.
- **An approval step that stops accidents and non-interactive runs.** `approve` and `purge` refuse unless stdin and stdout are both interactive terminals and no agent or non-interactive marker is present in the environment (`DISK_JANITOR_AGENT`, `DISK_JANITOR_NONINTERACTIVE`, `AGENT_SESSION`, `NONINTERACTIVE`, `CI`). `approve` shows *every* candidate (paged), then requires the **full plan digest** typed back; the digest is not printed on that screen, the human reads it from `disk-janitor explain`. `purge` requires the confirmation code printed by `purge --dry-run`. An approval is an HMAC-SHA256 over the plan digest, an expiry and a nonce, keyed with a per-user key file (mode 0600), valid 15 minutes by default (60 at most), single-use; the audit log records the approver kind. The MCP server has no approve tool and no purge tool. **This is not a security boundary against a process running as the same OS user** (next section).
- **Optional stronger approver (best effort).** `disk-janitor approve --approver dialog` takes the decision from a native confirmation dialog (`osascript` on macOS, `zenity` or `kdialog` on Linux) with a fixed argument vector and text built only from the plan id, a digest prefix and numbers (no file-system data). A process that merely drives a pty cannot answer it. It is only as strong as the desktop session (an agent that can click UI elements through accessibility permissions or a shared X11 session can still answer it), it is unavailable headless, and it never falls back to the terminal.
- **Nothing is unlinked by `apply`.** Candidates are moved with `rename` into `<state>/quarantine/<planId>/`, on the same file system only (no copy and delete). A manifest authenticated with the same HMAC key records the original paths so `restore` is a faithful undo and refuses to overwrite. `purge` deletes only items listed in an authenticated manifest, only after a TTL (7 days by default), and only after typed human confirmation.
- **Re-validation at apply time.** Every candidate is checked again against the plan: same device and inode, still a real directory, no symlink anywhere in the parent chain, nothing modified since the plan (the whole tree is re-measured), still inside the roots, not protected, **and still a catalogue item** (a `node_modules` next to a `package.json` and lockfile, a build output whose path is exactly one of the allowlisted names next to a manifest or inside a git repository, or an exact package-cache location), so a hand-forged plan cannot get an arbitrary directory quarantined. Git ignore state is not re-run at apply. No open file handles (when `lsof` is available). If anything differs the whole apply aborts before the first move. A swap that wins the race between the last check and the rename is detected afterwards by comparing the moved item with the plan and the move is undone.
- **Never follows symlinks.** Walks use `lstat`; symlinks inside candidates are moved along but never traversed or sized; key and audit files are opened with `O_NOFOLLOW`.
- **Protected paths always win.** `.git`, `.ssh`, `.gnupg`, `.aws`, `.config`, keychains, `.env*`, Documents, Desktop, Downloads, Pictures, Music, Movies, iCloud/Dropbox/OneDrive/Google Drive style sync folders, database data directories, names that look like secrets, and any candidate that contains a nested `.git`, an env file, private keys or database markers.
- **Hostile names.** Paths and git/docker output are untrusted. Terminal output escapes control characters, ANSI/OSC sequences, bidi controls and invisible code points (Unicode tag characters, variation selectors, fillers, zero-width and joiner characters); JSON output and plan files escape the same set; MCP output, including error and warning text, wraps every file-system string in `<untrusted-data>` frames. Plan files, approval records, manifests and config files are parsed with strict schemas and size limits.
- **Untrusted repositories.** git runs with an isolated environment (`GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` set to `/dev/null`, no attributes file, no excludes file, no hooks, no fsmonitor) and a repository whose own config defines commands (`filter.*`, `core.fsmonitor`, `core.hooksPath`, `core.sshCommand`, `diff.*.textconv`, `merge.*.driver`, `include.*`, credential helpers...) is skipped before anything that could run them. Your global gitignore is therefore not consulted; paths ignored only there are not offered.
- **State is serialized.** `apply`, `restore` and `purge` hold the same exclusive state lock; stale locks are taken over through an exclusive takeover gate so two waiters cannot both win.
- **Docker steps are labelled irreversible.** The approval screen names the daemon (`DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_CONFIG`) a prune will hit.
- **Tamper evidence.** Every action is appended to a hash-chained JSONL audit log. `apply` refuses to run on a broken chain.

## What this tool does not protect against (threat model limits)

- **The approval gate is not a boundary against a same-user agent.** Everything the gate checks (a TTY, five environment variables, a typed digest) can be satisfied by any process that runs as your OS user, has a shell and can allocate a pty (`script(1)`, `expect`, a pty library): it can run `disk-janitor explain`, read the digest and type it into `disk-janitor approve`. The repository's demo does exactly this. The approval key is also a file readable by that user, so such a process can forge an approval record, or simply run `rm`. The gate stops accidental runs, scripts and agent tool calls that have no terminal; it does not stop an adversarial or confused agent that has shell access under your account.
- **How to get a real boundary.** Make the approving identity something the agent's account cannot be:
  1. *Different OS user (recommended).* Create a dedicated account (for example `janitor`) that owns the state directory (mode 0700) and runs `disk-janitor` and `disk-janitor-mcp`; give it read/write access to the roots (group permissions or ACLs). Start the MCP server as that account (for example through a restricted `sudoers` rule or a socket-activated service) so the agent only ever talks to the server. The human runs `sudo -u janitor disk-janitor approve <plan id>` (or logs in as that account). The key file is then unreadable to the agent's account and `approve` cannot be run by it without the `sudo` credential.
  2. *Root-owned approval material.* Keep the approval key and the `approvals/` directory root-owned and let only a small root-run wrapper issue approval records after its own confirmation. The same principle: the verifier may run as the agent, but the key must not be readable by the agent.
  3. *OS dialog approver* (`--approver dialog`): a middle option when a separate account is not practical, with the limits stated above.
  A symmetric (HMAC) approval needs the verifier to hold the key, so any account that can run `apply` can also forge approvals; the options above work by making sure the account that runs `apply` is not the account the agent controls.
- **The audit log is tamper-evident, not tamper-proof.** The chain detects edits, deletions and reordering. It cannot detect truncation of the tail or a complete rewrite by someone who can write the file. Record the head hash (`disk-janitor audit` prints it) somewhere else if that matters.
- **Rename races cannot be eliminated without `renameat`.** Node.js has no directory-relative rename. The last re-check and the rename are separated by a very small window; a swap inside it is detected after the fact and undone, but a path component replaced exactly in that window is renamed before it is noticed. `restore` can, in a similarly tiny window, replace an *empty* directory that appeared at the target.
- **The open-file check is best effort.** It needs `lsof`; without it the check is off (`doctor` and `scan` say so). `lsof` run by a non-root user only sees that user's processes.
- **Not a backup.** Quarantined items stay on the same disk until purged; a disk failure or a manual delete of the state directory loses them.
- **Windows is not supported.**

## Dependency policy

Every npm package version, direct and transitive, is published on or before 2026-10-24T00:00:00Z. The lockfile is generated with `npm install --package-lock-only --before=2026-10-24T00:00:00Z --ignore-scripts`, direct dependencies are pinned to exact versions, installs use `npm ci --ignore-scripts` (CI included), and installs, tests, typechecks and builds run in a throwaway container rather than on a developer host. The core (`scan`, `plan`, `apply`, `restore`, `purge`, CLI) uses no runtime dependencies beyond Node.js built-ins. The MCP server uses `@modelcontextprotocol/sdk` and `zod`. `.github/dependabot.yml` uses a 7-day cooldown and ignores semver-major updates of `typescript` and `@types/node`. GitHub Actions are pinned to commit SHAs and the workflow token is read-only.
